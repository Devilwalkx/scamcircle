# Decisions

Draft record of design choices. Each says what was chosen, why, and what is still open. None of this is legal advice or certification.

| ID | Decision | Why / limits |
|---|---|---|
| D-001 | **Competitor and legal sources were not read.** The build sandbox could reach only npm and GitHub. | Nothing in this repo claims that a competitor lacks a feature, or states what UK GDPR / ICO guidance requires. The spec's Norton and Apple links, the ICO guidance and the Data (Use and Access) Act 2025 are all **unverified here**. Open item for a human. |
| D-002 | **No server.** Everything is local. Sharing is manual: the app creates a text string and the person moves it (copy, paste, share sheet). | The product spec proposes a managed backend; that needs supplier, region and cost decisions that were not made. Serverless sharing proves the crypto and the UX honestly, but there is no delivery receipt, push, or directory. The app says "not delivered until you send it". |
| D-003 | **Network access is blocked at the Android manifest** (`INTERNET` is in `blockedPermissions`). | The strongest simple proof that the app cannot send case content anywhere on the phone. Consequence: no future feature may use the network without a deliberate change and a new data-flow review. The web build is served over HTTP(S) by whoever hosts it; that is different (see D-012). |
| D-004 | **Rule-based indicator engine, English only, no OCR, no cloud AI.** | The spec forbids cloud AI/OCR for private content. Screenshots are shown only while the person types what they say (D-009). Non-English, unreadable or very short text yields "cannot assess", never a guess. |
| D-005 | **No "safe" result exists anywhere.** Outcomes are: pending / not verified / indicators found / specific verification step completed. | The text-level engine can only say what it saw. A test scans engine and outcome strings for reassurance wording. Even a completed step says "this does not make any payment safe". |
| D-006 | **A verification step counts only if the route was independent AND the answer conclusive.** Numbers, links and threads supplied by the message are never independent. A trusted route added *after* the message arrived does not count. | Spec: "callback details supplied by the suspicious message are not independent evidence". |
| D-007 | **Sharing cryptography is an HPKE-like composition**: X25519 (ephemeral + sender static) -> HKDF-SHA256 -> XChaCha20-Poly1305, with the header as authenticated data. Primitives from `@noble/curves`, `@noble/hashes`, `@noble/ciphers`. | No homemade primitives. **The composition is not HPKE and has not been independently reviewed. It needs review before any real use.** Known limits are listed in `src/sealedbox.ts` and THREAT_MODEL.md. |
| D-008 | **Contacts are verified by comparing 4 made-up words** (about 66 bits of the key's hash) out of band. Unverified contacts cannot receive cases or be heard from. A different key under a known name demotes the contact to unverified until re-checked, and the old key is never replaced silently. | The UX is a simple Yes/No. A Yes is easy to tap without really comparing. The UX and the word length need independent review and usability testing. |
| D-009 | **Pictures are never stored, and are never analysed.** They are re-encoded (EXIF removed), checked, and shown while the person types the text (updated by D-021 for cropping and sharing). | Minimises third-party data. The re-encode step may leave a temporary file in the app cache (open item, DATA_FLOWS). No image crop UI was built; redaction works on the typed text. |
| D-010 | **Redaction is by the person, on the text.** The app suggests (phones, e-mails, bank details, postcodes) with all suggestions on by default; the person can switch each off and add their own words. The share screen shows exactly what will be sent. The sealed content is produced by the same function as the preview. | Names and addresses are not auto-detected. Third-party data in a message is the person's call; see PRIVACY_REGISTER. |
| D-011 | **Revocation is local plus an optional "stop code".** Revoking marks the request revoked here (replies are ignored) and creates a sealed notice the reviewer's app can import to close and clear the request. | Cannot recall anything already seen, copied or screenshotted. If the person does not send the stop code, the reviewer's app still shows the request until it expires. Expiry is enforced by each app's own clock. |
| D-012 | **Web build is a convenience for demos and tests, with weaker key protection** (non-extractable WebCrypto key in IndexedDB; any script on the origin can ask it to decrypt; clearing site data destroys the key). The Android APK is the intended target. | Same trade-off as the sibling AccessChain app. |
| D-013 | **Single encrypted blob for the whole vault**, rewritten on every change, with version bound into the authenticated data. | Simple and safe for this size. It does not scale to many large cases, and rollback is only detected when the version field is edited (not if an attacker restores both the old ciphertext and the old version). |
| D-014 | **Recovery secret + encrypted backup text.** Losing the phone without a secret and a backup means permanent loss. Restoring an old backup re-applies this phone's deletion tombstones. | Spec 1.2. A restore puts the backup's identity key on the new phone; the old phone should be erased. |
| D-015 | **No notifications and no logging of content.** `redactForLog` exists and tests ensure core code has no `console.*`. | Spec: generic notifications only. None are built because they would need either a server or a permission the app does not request. |
| D-016 | **UI (revised in the Android pass; the earlier "no tab bar, four big buttons" design is gone).** Top bar with Back and Settings, a bottom bar with People, Check (centre, one big action on Home) and Requests; system Back unwinds one step then goes home; in-app text size and light/dark on top of Android's own settings. See docs/SCREEN_DECISIONS.md. | Based on a real-phone test of a sibling app (text overlapping buttons), then the shared design foundation. Guarded by the large-text layout audit. Not tried by a fresh user (docs/USABILITY_SESSION_PLAN.md: NOT RUN). |
| D-017 | **Android edge-to-edge uses `react-native-safe-area-context` on all edges.** The built-in React Native `SafeAreaView` does nothing on Android. | Lesson from AccessChain. `?insets=44,48` simulates bars on web; a test fails if the fix is removed. |
| D-018 | **Task-switcher / lock-screen hiding is not implemented.** | Would need `FLAG_SECURE` through a native module. Documented as a gap rather than faked. |
| D-019 | **Test build is signed with the Android debug key** and published as a pre-release. | Fine for sideloading to try it. Not for any store. |

| D-020 | **Share-in uses `expo-sharing` (Expo SDK 58) with its Android config plugin**, not `expo-share-intent`. | `expo-share-intent` 8.0.1 declares `expo ^57`, which does not match this app's SDK 58. `expo-sharing` is part of the SDK, needs no permission, and offers both directions. Only unresolved payloads are read: the resolving call can try to fetch web addresses, and the app has no internet permission and never opens links. Verified on the emulator only through an `adb` SEND intent, never from a real sender app. |
| D-021 | **A picture can be trimmed and handed to the share sheet, nothing else.** | Asked for by the Android pass. The copy is NOT encrypted by ScamCircle and goes to whichever app the person picks, so the screens say so. The picture is not analysed and the UI says "This picture was not analysed". Trimming uses stepper buttons (no dragging) so it works with a screen reader and large text. Covering parts (blur or boxes) is not built: only removing edges. Temporary copies stay in the app cache until the phone clears them |
| D-022 | **Two ways to ask someone**: plain text through the person's own messaging app (simple, not encrypted by ScamCircle), or a private encrypted code for a checked contact. | The code route needs both people to have the app and compare words, which is a lot to ask. Both end with the same honest card: not sent, no delivery receipt, no reply notification |
| D-023 | **The same-phone "demo helper" is a labelled demonstration only**, moved to Settings, Demonstration tools, with a loud strip; it is never offered in ordinary use. The first-run example is a single marked case with no helper or trusted number. | A local simulation must not be presented as working collaboration, and example data must not be mixed with a person's own |
| D-024 | **Results are four separate things**: found, could not check, who sent it (Not verified unless the person checked another way), and the next independent check. No string can say safe, genuine or fine to pay (a test scans every sample). | Absence of indicators is not evidence of anything |
| D-025 | **Unfinished text is sealed at rest** (same device key, own item id, not in backups) and cleared when checked, cleared by hand, or erased. | The pasted message may be private |
| D-026 | **Block `USE_BIOMETRIC`, `USE_FINGERPRINT` and the install-referrer service permission** that libraries pulled in (found by checking the built APK). | The app uses none of them |

## Open items for people (not done here)
- Independent review of the sharing composition and the verify-by-words UX.
- Check the Norton, Apple and ICO sources named in the spec; confirm competitor position and legal basis.
- Article 10 / criminal-allegation handling: nothing is built to publish or aggregate allegations, and there is no public list; the legal position on *storing* a person's message that alleges an offence still needs a decision (PRIVACY_REGISTER).
- Backend, supplier and region choices if a server is ever added.
- Real-device testing (never run on a phone by the builder).
